# Kshitij — Project Context and Working Agreement

Last updated: 2026-10-24

## 1. Project overview

Kshitij is a flood-risk decision-support prototype focused on Vijayawada and the Krishna River.

Purpose: explore reproducible flood-extent modelling and communicate possible flood scenarios through a polished, professional interface.

Important limitations:
- This is a research/prototype project, not a live emergency-alert system.
- Simulated outputs must be clearly labelled as simulations.
- Do not imply model outputs are verified predictions or ground truth.
- Historical maps can serve as reference material but are not automatically authoritative validation data.

Planned stack:
- Python, NumPy, Rasterio for geospatial modelling and raster processing.
- PostGIS for spatial database functionality.
- Django/GeoDjango is a possible backend.
- React + MapLibre is a possible frontend.
- Cloudflare Pages is a deployment candidate.
- Backend, hosting, storage, and API architecture are not all finalized. Do not prematurely lock in infrastructure choices.

## 5. Completed milestone: M1.1 flood connectivity

Files:
- `src/kshitij_model/__init__.py`
- `src/kshitij_model/connectivity.py`
- `tests/test_connectivity.py`

Function:
`compute_flood_extent(elevation, source_mask, water_level)`

Behavior:
- Returns a Boolean NumPy array with the same shape as the elevation input.
- Uses 4-neighbour breadth-first search.
- A cell is floodable if its elevation is finite, is at or below the water level, and is connected to an eligible source.
- Diagonal-only contact does not establish connectivity.
- Above-threshold cells and invalid cells block traversal.
- Sources must be valid and at or below the threshold.
- If no eligible source exists, returns an all-false mask.
- Input arrays remain unchanged.
- Input types and edge cases are validated.

## 7. DEM investigation findings

Observed properties:
- Tiles are 3600 × 3600, one-band float32 rasters.
- CRS: EPSG:4326.
- Pixel size: one arc-second, approximately 30 m.
- `AREA_OR_POINT=Point`.
- No GDAL NoData tag (`src.nodata is None`).
- No internal mask or alpha; mask flags indicated all pixels valid.
- No `-32768`, NaN, or infinity values were found in the inspected arrays.
- N16E079 elevation range: 28.0 to 912.890 m; no negative pixels.
- N16E080 range: -1.5 to 564.940 m; 23 negative values and 18,513 exact zeros.
- N16E081 range: -4.5 to 237.011 m; 496 negative values and 3,679,242 exact zeros, approximately 28.39%.
- The extensive zero region in N16E081 represents ocean/water-body treatment, not automatically invalid elevation.
- Official product XML documents vertical datum WGS 84 Geoid EGM08, vertical CRS EPSG:3855, metres, and `-32767` as the product void sentinel. The inspected tiles reported zero invalid pixels in the XML metadata.
- HEM is Height Error Mask/standard deviation information, not a validity mask.
- Other auxiliary layers include WBM (Water Body Mask), FLM (Filling Mask), and EDM (Editing Mask).

Important preprocessing risk:
**Ocean zeros must not be treated as ordinary urban land.** At water levels of zero or higher, an unconstrained connectivity model could flood extensive ocean cells. Future preprocessing must decide how to use an explicit study-area boundary and/or WBM. Do not simply declare all zero or negative elevations invalid.

### One known review finding: next task

The assistant independently inspected the branch source and found one narrow potential bug:

`_validate_nodata()` accepts arbitrarily large Python integers because they are `numbers.Real`, but later `np.isnan(nodata)` or `np.isinf(nodata)` can fail to coerce a huge integer (for example, `10**100`) into a NumPy-supported numeric value.

The next task is to fix this edge case with a minimal patch and focused regression test. Either safely support the value without losing exact-equality semantics or reject it intentionally during validation. Do not blindly cast all sentinels to float.

Preserve:
- Backward compatibility when `nodata` is omitted.
- `None`, finite sentinels, NaN/infinity behavior, valid negative elevations.
- Exact equality semantics.
- Input immutability.
- `DEMConfig.nodata_value = None`.

Run the full test suite, Ruff lint, formatting check, and `git diff --check`. Inspect the complete diff and preserve untracked files.

If all checks pass, a single focused commit is appropriate:
`fix(model): validate large NoData sentinels safely`

Do not push, open a PR, or merge as part of this task unless the user explicitly asks.

## 9. Next roadmap after the NoData fix

Do not begin this work until the NoData fix has been reviewed.

### Phase A: Raster preprocessing
- Define an explicit study-area boundary for Vijayawada/Krishna River.
- Crop source DEMs to the study area while preserving CRS, affine transform, bounds, dimensions, and relevant metadata.
- Mosaic only when necessary and ensure pixel-grid alignment.
- Decide how to use the Copernicus WBM and explicit urban/study-area boundaries to prevent ocean-zero cells from being treated as land.
- Preserve valid zero and negative elevations where appropriate.
- Handle NoData/masks correctly and record preprocessing provenance.

### Phase B: Prepared-raster adapter
- Connect prepared Rasterio data to `compute_flood_extent`.
- Keep source masks and water-level assumptions explicit; do not silently infer hydrological inputs.
- Test raster metadata, cropping, transforms, invalid/valid zeros, partial and all-invalid rasters, no-overlap behavior, unsupported bands/dtypes, missing CRS, and manifest behavior with offline synthetic fixtures.

- Compare selected historical scenarios against reference materials, including the AP-SAC map dated 13 September 2024, while clearly stating limitations.
- Do not describe a historical map as ground truth without independent evidence.

### Phase D: Product and deployment
